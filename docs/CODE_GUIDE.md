# A beginner's guide to the code

The app uses regular Django patterns and server-rendered HTML. There is no separate front-end application, API layer, build system or database server to learn.

## Where to start

| File | Responsibility | When you would edit it |
| --- | --- | --- |
| `templates/base.html` | Shared header, navigation and page wrapper | Change branding or navigation |
| `templates/budget/dashboard.html` | The annual dashboard HTML | Change labels and layout |
| `static/style.css` | Colours, spacing and responsive styling | Change the appearance |
| `config/urls.py` | Maps browser addresses to Python functions | Add a new page |
| `budget/views.py` | Handles page requests and form submissions | Change a page's workflow |
| `budget/forms.py` | Validates user input and saves entries/splits | Add or change an input field |
| `budget/models.py` | Describes the records stored in SQLite | Change what information is stored |
| `budget/services.py` | Calculates monthly cash and category totals | Change a budget calculation |
| `budget/imports.py` | Parses and saves CSV transactions | Add bank-format support |
| `budget/admin.py` | Configures Django's built-in management pages | Change the admin interface |
| `config/settings.py` | Django and security configuration | Configure the application |
| `budget/tests.py` | Budget calculation tests | Check budgeting behaviour |
| `budget/test_security.py` | Login, request protection and invalid-input tests | Check security boundaries |

## Follow one request

1. The browser visits `/add/entry/`.
2. `config/urls.py` chooses the `add` function in `budget/views.py`.
3. `EntryForm` in `budget/forms.py` supplies the input fields.
4. `templates/budget/form.html` renders those fields as HTML.
5. Clicking Save sends a POST request, including Django's CSRF token.
6. The view calls `form.is_valid()`. Invalid values return to the form with an explanation.
7. A valid form saves an `Entry` and its `Allocation` records inside a database transaction. A transaction means they succeed together or are rolled back together.
8. The browser returns to the dashboard, which calls `report()` in `budget/services.py`.

## Vocabulary used in Python

- **Model:** a Python class describing a database table. An instance is one row.
- **Entry:** one planned or actual income, expense or internal transfer.
- **CategorySchedule:** one category’s amount, recurrence and due dates for a budget year. It has no bank account.
- **Allocation:** the part of an entry assigned to a category.
- **ForeignKey:** a reference to another record; for example, an entry's account.
- **QuerySet:** a database query such as `Entry.objects.filter(actual=True)`.
- **pk:** the unique database identifier for a record.
- **clean():** Django's validation hook, used to reject invalid input.
- **Decorator:** a line starting with `@` that wraps a function. `@login_required` checks the user is signed in before running a page handler.
- **Migration:** a versioned database change, generated by Django from model changes.

## The money rules

Money is saved as whole cents: $12.34 is `1234`. User forms convert dollars to cents. Reporting converts cents to exact decimal dollars for display; it does not calculate money with approximate floating-point numbers.

An entry starts as planned (`actual=False`) or actual (`actual=True`). Planned entries capture `original_cents`, which is retained when their forecast amount changes. Splits also preserve their original amounts. Marking or matching a planned entry as actual replaces that plan; it does not add a second expense.

For buckets, `remaining_allowances()` subtracts separately recorded actual purchases from the same month's remaining planned allowance, matching by account and category. `monthly_cash()` calculates the primary account. `category_spending()` compares original, actual and forecast spending. Transfers appear in cash flow but not spending totals.

A category schedule supplies its original budget and current expected spending per due month. Open-month spending forecasts use the larger of this expected amount and entry-based spending; closed months use actual spending. Schedules never create bank movements, so primary cash still comes entirely from entries. The original schedule is retained when edited, and schedules for different years are independent.

Closed months use actual movements only. They are not automatically closed based on today's date: you choose when the imported records are complete.

## Safe ways to make changes

For appearance changes, edit HTML/CSS and refresh the browser. For calculation changes, add a test with a concrete money example and run `python manage.py test`. The tests use their own temporary database, not your household database.

CSV import tests use fictional records in `budget/test_card_import.py`; `budget/test_migrations.py` checks that the card-import upgrade retains existing records. Bank category hints are stored separately from your budget allocations.

For model changes, run `python manage.py makemigrations` and review the generated file, then back up your real database before `python manage.py migrate`. Do not edit SQLite directly to change its structure.

Keep Django's password hashing, login handling, HTML escaping and CSRF tokens in place. Avoid adding `|safe` to imported descriptions, raw SQL built from user input, or your own password storage.

The security tools are optional development dependencies; they are not needed to run the app. Formatting expands compressed statements into conventional Python and HTML without introducing a new application architecture.

Income can optionally set `Entry.income_month`, stored as the first day of the chosen month. A blank value uses the transaction month. Reports query budget income separately so December pay allocated to January appears in the next year’s spending comparison, while cash remains in December. Recurring entries preserve the month offset; imported transactions matched to a plan keep its income month.
